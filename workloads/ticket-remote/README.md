# Ticket Remote

Public manager for `ticket.jolkins.id.lv`.

Start with [CURRENT.md](./CURRENT.md). That is the live Ticket product map: open the signed-in page, get a live picture, swipe the oval, open a fresh unused ticket, or request a control code.

For agent rules and live-page proof, use [AGENTS.md](./AGENTS.md). For start, stop, and health, use the [Ticket runbook](../../docs/runbooks/MODULE_TICKET_REMOTE.md).

The service checks Ticket membership and relays the phone stream to signed-in browsers. Authenticated browsers write bounded Ticket actions directly to SpacetimeDB; the Pixel visually executes those durable rows. Browsers never receive direct phone control.

## Local Development

```bash
make test
make spacetime-build
make web-client-build
```

The reusable real-GPU HDR check lives at `web-client/client-hdr-real-gpu.html`. Serve that directory from localhost in a browser with WebGPU enabled; it renders and reads back the internal 1x identity patch plus the 2x, 3x, 4x, 5x, and 6x user-selectable patches through both the linear-canvas and encoded-sRGB paths. This verifies the GPU signal values, not physical display brightness.

## Runtime Model

- General mode: linked users can view the ViVi ticket stream together.
- Control-code requests: a linked user enters 2-8 digits in the webpage, a member-only Spacetime reducer queues the request, the phone automates ViVi, and the requester browser accepts and freezes one exact generated stream frame locally. The ordinary SDR frame remains the capture authority and is always prepared as the fallback. When browser HDR is active, the same HDR view continues through the dialog and phone execution, and the result card may hold the matching HDR frame only after its GPU and compositor presentation milestones complete. Otherwise the browser uses the SDR image only after it has decoded, remained visible through two paint frames, and passed an on-screen bounds check. Assigning an image URL is not an acknowledgement, and Pixel must not send ViVi result screenshot bytes to the browser.
- A requester can submit at most two code requests per rolling minute. A second successful request replaces the visible result on that user's page.
- Registration admission is per authenticated account: one admitted physical registration every 30 seconds and ten counted admissions per rolling hour. Admins and owners obey the same limits by default; their account-persistent SpaceTime preference may bypass quotas for testing, with bypassed actions retained as non-counting audit events.
- Membership authority is enforced atomically in SpacetimeDB as well as in the admin page: administrators may add and remove ordinary members, only owners may create or change administrator and owner accounts, unknown roles are rejected, and the final active owner cannot be demoted or removed. Transfer ownership by creating a second owner first.
- ViVi account management is available only to an active owner. Saving and clearing are revision-fenced database operations and do not touch the phone. The standard separately confirmed account switch enters the shared phone-mutation lane and preserves ViVi app data and its linked-device identity. From an exactly proved ticket detail it retains a private detail identity, navigates through ViVi's own account controls, proves the in-app sign-out, writes each saved field once, submits once, and follows at most three visually typed, journaled steps back to that same detail. A session-only checkbox is off by default and is captured when the confirmation opens. When selected, the phone still tries to restore the original ticket first; only if the original is unavailable may it find and open the newest unused ticket without activating it, or finish successfully after proving that no unused ticket is available. If ViVi is already signed out, it begins from the proven login screen without a prior detail identity to restore. It never repeats an uncertain physical step. A distinct, strongly warned full-reset action deliberately runs one `pm clear --user 0 com.pv.vivi` before its bounded sign-in flow. That deletes all local ViVi app data and the linked-device identity, so an external device-link reset may be required. Neither non-destructive mode falls back to full reset, and the optional fallback cannot alter the full-reset request. MFA/additional verification, device linking, profile choice, CAPTCHA, onboarding, unknown surfaces, and uncertain logout transitions stop as attention-needed. Every successful ticket outcome requires a fresh visual proof bound to a later positive encoded-frame watermark.
- The single backend credential is deliberately plaintext in a private SpacetimeDB table and is returned in clear text through a caller-filtered owner view. This puts database operators and backups inside the accepted trust boundary. The Pixel service identity can read the exact matching row only while a pending/running re-authentication command exists. With the new checkbox off, the current standard command remains exactly version 3, uses a `vivi-logout-login-` request ID, and includes only `logoutInApp: true` in addition to the request ID and credential revision. With it on, the same reducer receives version 4 under the non-overlapping `vivi-logout-redetect-login-` namespace and the command adds exactly `redetectAfterLogin: true`. Queued requests preserve the selected mode with the same exact flags. The separately confirmed full-reset command remains version 2 with only `resetAppData: true`. Version 1 and its `vivi-reauth-` prefix remain accepted for stale-page and in-flight compatibility without being produced by the current admin page. Public projections contain no email or password.
- Other viewers stay connected to the shared raw ticket stream. They may briefly see the real phone open and close ViVi's control-code UI, but they never receive direct control.
- Browser users connect directly to the Ticket SpacetimeDB database for authenticated product state and code-request actions. Browser diagnostics instead travel over the existing authenticated video WebSocket so `ticket_remote` can validate and sanitize them before the sidecar writes them to the central operational log. `ticket_remote` is not a second control authority.
- Browser users never talk directly to the Pixel. Immediate Ticket actions and admin re-detection schedules use authenticated Spacetime reducers that atomically create a sanitized action projection and a durable command row; `ticket_remote` remains the authentication and video-relay boundary.
- Pixel keeps one subscription for every pending Ticket command and one dispatch ledger shared with reconnect polling. The subscription is the warm path; polling is catch-up and acknowledgement recovery. Registration uses one exact-ticket preparation fence before dispatching an uninterrupted 800 ms stroke. The same action may make one final stroke only after Android conclusively completed the first, two fresh frames still prove the exact same ticket unactivated, and the complete fence passes again. Ambiguous outcomes and failed readiness checks stop without another touch; no retry child is created.
- A single idempotent Spacetime finalizer commits the terminal action, activation history, interaction state, refresh schedule, exact command retirement, lane release, and at most one waiting-intent promotion in one transaction. Network-loss delivery may repeat an identical result, but a conflicting replay changes nothing and can never cause another phone gesture.
- Ticket action v3 has seven targets: open the latest unused ticket, open and register it, register the currently open ticket, show the recently activated ticket, return to the latest unused ticket, re-detect the latest ticket, and non-mutating `prove_current`. Every mutating target acquires the single phone-mutation lane, observes fresh rooted frames, performs at most one proven transition at a time, and publishes one terminal sanitized result. `prove_current` only observes two agreeing frames and never navigates, recognizes a date, taps, or registers.
- The public action projection contains only opaque action identity, target, progress, current visual view, switch availability/expiry, frame watermark, bounded reason, and timestamps. When an unused ticket is proven, a separate five-minute projection may contain the normalized slider rectangle bound to that exact action and stream watermark so the browser can place a transparent local range input over the live picture. Dates, ticket text, recognized glyph output, raw device coordinates, screenshots, and pixels remain on the phone.
- Spacetime is the sole business-clock authority. It computes quota eligibility, schedules quota projection boundaries, creates the 15-minute smart-switch anchor, rejects expired switch requests, and owns delayed refresh/re-detection rows. Pixel retains only private visual matching evidence, physical-action checkpoints, bounded action timeouts, and transport recovery; none of those phone-local timers may originate a future product action.
- The production backend is the physical Pixel through the private `ticket_phone_bridge`; `ticket_remote` relays media directly from that bridge while SpacetimeDB owns durable stream intent and commands.
- Runtime diagnostics are SpacetimeDB-only in `operational-logging-prod`, under `operationallog_event` rows with `domain = 'ticket'` and six-hour retention. The existing minute sampling for routine informational events remains in the central reducer. `ticket_remote`, the phone bridge, and Pixel ticket automation must not leave local runtime log files behind.
- Browser diagnostics are best-effort: they queue until an authenticated video socket is open and are removed after the WebSocket accepts the send. The server accepts only the reviewed 79-name event vocabulary, caps both each socket and the whole service at 60 messages per minute, removes private keys and values, and keeps the first-rendered-frame lifecycle acknowledgement independent from diagnostic admission. It does not trust browser correlation IDs or acknowledge database persistence; it derives correlation from the authenticated browser session.
- Successful Ticket mutations never wait for audit logging. Audit rows use a separate asynchronous 750 ms deadline, and central cleanup removes up to 1,000 expired rows every five minutes so it safely outpaces the bounded browser path.
- Public video is H.264 over the existing HTTPS WebSocket: the active phone backend emits one private rooted hardware H.264 stream, and `ticket_remote` fans it out to authenticated browsers without public media ports. The browser media socket requires the exact schemeful origin configured by `PublicBaseURL`; this remains valid behind Cloudflare Tunnel without trusting the tunnel-to-origin Host as browser authority.
- Active authenticated members may opt into browser HDR with a private account setting that defaults off and restores across sessions and devices. Every member may persist exactly 2x, 3x, 4x, 5x, or 6x; missing, retired, or invalid saved state resolves to 4x. Browser v2 reuses the ordinary decoder's `VideoFrame` on an isolated opaque WebGPU canvas. Its internal 1x mapping is exactly the SDR source for safe handoff and diagnostics; selected boosts give every non-black color a black-anchored lift driven by the brightest RGB channel. One shared gain preserves hue and channel ratios, exact black remains zero, near-black stays restrained, and ordinary ticket red, orange, green, blue, gray, and white all brighten. The retired owner engine preference remains a private compatibility tombstone; ordinary members use the fixed v2 engine without an engine selector. Each genuine start or foreground lifecycle recovery uses a fresh canvas configured for extended tone mapping and unrestricted dynamic range. Its first visible copy is the exact SDR frame with only the bounded 1.25x request patch, and that same canvas remains topmost for two compositor opportunities. After freshness, lifecycle, boost, generation, and control-code checks, the full all-color target is copied into that same canvas without replacing or demoting it; target GPU completion and a post-copy compositor opportunity are required before success. After the first completed presentation, scrolling away and back or a transient video/control connection, stale-frame, or next-keyframe wait keeps the last bright canvas topmost without rebuilding it. The existing stream spinner stays above the held canvas without dimming it and is the only recovery cue while exact proof is false and every phone-changing control, including control-code entry and submit, remains passive. Only an online browser, open video socket, fresh live direct SpaceTime state, fresh streaming server status, and an exact new frame restore live HDR on the same surface and hide the spinner. Unsupported capability, explicit stop, backgrounding, superseded settings, rendering or device failure, invalid output, and other hard authority loss still reveal SDR immediately without changing the phone capture or storing media. The source remains BT.709 SDR, so the remap does not restore highlights discarded at capture. Browser configuration, GPU completion, observed compositor opportunities, and holdover telemetry describe intent and cannot prove a paint or emitted HDR brightness; controlled observation on a physical iPhone remains the release gate.
- HDR remains active while the control-code dialog is open and while the request is queued or running. SDR proof frames continue without HDR backpressure. Once the exact request, stream epoch, and frame sequence are accepted, later HDR frames cannot move the result. The result overlay sits above the held HDR canvas and becomes transparent only after that exact HDR frame is fully presented; its close control remains available and its 60-second expiry runs without a visible countdown. A frame mismatch, bounded presentation timeout, unsupported HDR, staleness, backgrounding, or GPU failure keeps or restores the opaque frozen SDR result. Dismissal and cleanup dispose the held HDR surface and reacquire from a fresh current-epoch SDR frame rather than resuming the old surface.
- Pixel capture uses one crisp SDR hardware profile: 994 px target width at about 8 Mbps, BT.709 limited color, and one H.264 encoder producing one complete, independently decodable picture per second. Its 994x2046 visible frame pads to a decoder-safe 1008x2048 H.264 surface. The same source feeds SDR and browser HDR. Startup, slider, Ticket-action, and control-code work coalesce refresh demand into one immediate next picture; they do not increase the frame rate or start a burst.
- Browser delivery remains bounded per viewer: one independent picture may be awaiting a complete-message receipt and only the newest independent picture may wait behind it. Source sequence gaps are safe because every picture is independently decodable. The relay requires the exact rooted source contract: `avc1.42C028`, `hardware-h264-annexb`, `root_hardware_h264`, `root_display_capture`, `app_process_mediacodec_surface_secure_screen_capture`, `rootCapture=true`, the `hardware_h264_crisp_all_intra_1fps` quality profile, the fixed `red_blue_swap_high_brightness_sdr_gpu_paint_r1.08_g1.05_b1.03` correction, BT.709 limited SDR signalling, and a nominal configured target of 8,000,000 bit/s. Its 1080x2424 source is cropped left/top/right/bottom by 4/200/3/3 pixels to 1073x2221 and encoded as 994x2046, with explicit `all_intra`, `fps=1`, `sourceFps=1`, and `keyframeIntervalFrames=1`; a missing or contradictory field and every delta picture fail closed before reaching viewers. Both TSF2 and TSF3 remain accepted during the rolling envelope transition, but a legacy TSF2 producer must advertise the same canonical media fields. The relay grants coalesced ordinary capture opportunities but never changes the phone's fixed one-picture-per-second ceiling, resolution, bitrate, color, or all-intra encoding. Each config advertises Feedback v2 with a per-socket config generation. A valid exact-epoch/generation cumulative `receivedSequence` grants the next delivery credit before diagnostic rate limiting; v1 remains diagnostic-only. The relay coalesces all usable visible-viewer credit into one connection- and epoch-fenced 2.5-second ordinary `capture_demand`; the next phone binary completes that opportunity even when frame admission rejects it, and a missing result is retried only at expiry while useful credit remains. Proof, keyframe, startup, and prewarm capture bypass this ordinary gate and consume any already-pending ordinary opportunity, while an older Pixel safely ignores the additive message and keeps legacy periodic capture. A slow browser write may use the picture's remaining absolute three-second source-freshness budget instead of an unrelated 250-millisecond cutoff. After a successful write, a separate three-second receipt-liveness deadline bounds the transport debt; a complete stale picture can restore delivery credit but still cannot become visible authority. If this cutover must be reversed, roll the Pixel back to its legacy TSF2 producer first; the still-compatible relay can consume it. Then restore the older relay release. Never expose the older relay to the new TSF3-only producer.
- New streams advertise the 93-byte `TSF3` frame envelope. It carries epoch, sequence, capture-attempt and codec-generation identity plus monotonic capture, codec, and emission stage times. The relay immediately runs a four-timestamp clock probe on the private Pixel media socket, validates the echoed bounded result, converts every stage to UTC, and writes the mapping generation and uncertainty into the frame. One-way config/health samples preserve TSF2 continuity but never authorize TSF3 freshness, and a delayed first frame is never treated as a clock sample. The browser uses an equivalent generation-fenced probe on its authenticated video socket. Missing `frameEnvelope` remains `TSF2` during rolling compatibility. Frames must match the current config epoch and increase sequence strictly; a new epoch clears cached visual authority, while sequence gaps remain safe. The public `live` flag and `streamVerdict=live` require conservative `LIVE_FRESH` age; `LIVE_OK` and `DEGRADED` remain explicitly separate visual-continuity states and cannot suppress recovery or authorize an action. The canonical limit is 2 MiB of encoded H.264 payload plus the selected 29-byte TSF2 or 93-byte TSF3 envelope. Phone health uses one replaceable latest-state slot, while accepted ticket transitions use a lossless 64-event FIFO with retry; the normal 40-second stall matrix remains lossless within that bound, and overflow is an observable reconnect/reject fail-safe rather than a replay promise. Database delay cannot block media ingestion. Quiet private sockets use Ping/Pong liveness, reconnect with equal jitter, and reset backoff after a healthy connection. An already-desired relay loop also owns an in-flight handshake, so parallel wake requests join it instead of cancelling and redialing. Pixel services Ping and side-effect-free clock probes immediately after upgrade, before serialized phone preparation, while media commands remain disabled until atomic current-generation registration. Quiet public viewer sockets use the same bounded idle-then-Ping check; a failed probe closes only that viewer and does not change global source health. TSF2/TSF3 still carry no result, request, or requester identity. The first-party browser emits an `arm` hint only after its local Spacetime view has matched an owned real control-code row. The relay does not receive that row and does not verify requester ownership; it treats every hint as untrusted viewer-local scheduling input, strictly fenced and bounded so it can affect only the sending viewer. The arm lasts at most the durable request's five-minute workflow window; only when the exact public result marker arrives does the separate five-second delivery budget begin, releasing a current-config, current-epoch picture at or above that sequence. A marked delivery timeout closes only that viewer so its normal reconnect path can retry on a fresh socket within the durable workflow deadline. The hint contains no request or private identifiers, keeps the existing one-slot queue and receipt debt, clears on exact presentation, configuration replacement, close, failure, or expiry, and never changes another viewer or global source health. Every released picture still obeys the same three-second freshness deadline.
- Interactive browser UI uses ArrowJS for changing presence, status, stream, and control areas. Keep static or no-JS pages simple until they need browser-side interactivity.
- Edit browser UI in `web-client/`, rebuild with `make web-client-build`, and verify the deployed page mounts the Arrow-backed path.

## Privacy and Trust Boundary

- Requester-private data is the exact request digits, exact returned value, and locally held result presentation. Digits and requester email stay in private records, the exact result is routed only to the requester, and the browser holds either the exact HDR canvas frame or its frozen SDR fallback locally instead of uploading a phone screenshot or storing image bytes in SpacetimeDB.
- The live H.264 stream is shared among all authorized linked members. Every connected member receives the same phone frames and may see ViVi's control-code screen while a request runs, so linked membership is the media privacy boundary; requester-private result delivery does not make the live stream requester-private.
- The same shared-stream boundary applies during an owner-triggered ViVi account switch or full reset by explicit product choice. Linked viewers may see the account controls, login screen, and entered email on the live phone picture; there is no temporary privacy curtain. Password transport remains limited to the private database views and the Pixel process, and password values must not enter commands, logs, health, screenshots metadata, shell input, or clipboard state.
- SpacetimeDB's public tables are sanitized operational and activity projections. They may expose backend and stream state, viewer counts or public IDs, request status, timing, and non-secret proof markers, but they must not contain exact digits, email addresses, exact result values, or result images. Those values remain in private records or requester-only delivery paths.

## Availability Model

Production currently depends on one kitty-gration host and one physical Pixel. State and configuration are recoverable, but there is no automatic host or phone failover; see [Ticket Remote disaster recovery](../../docs/runbooks/TICKET_REMOTE_DISASTER_RECOVERY.md) for the recovery and standby requirements.

## Runtime Containment

- The public tunnel, phone bridge, and Spacetime sidecar are separated onto three dedicated Docker networks. `ticket_remote` is the only service present on all three, so the tunnel cannot directly reach the phone bridge or signing sidecar and unrelated workloads cannot directly reach any Ticket service.
- Docker stdout/stderr retention for the four Ticket runtime containers is capped at three 10 MB local-driver files per container. Durable Ticket diagnostics remain in the bounded central SpacetimeDB operational table.
- The Ticket Cloudflare tunnel runs as the owner of its read-only credential file, with a read-only root filesystem, all Linux capabilities dropped, no privilege escalation, and a 64-process ceiling. The production cloudflared image is pinned by digest. If credential ownership changes, update `ARBUZAS_TICKET_TUNNEL_UID` and `ARBUZAS_TICKET_TUNNEL_GID` together after a mirror pull and ownership check.
- Authenticated browser sockets are capped at four per browser session, eight per member identity, and 64 across the service. Closed sockets immediately release their capacity.

- the Spacetime private signing key is mounted only into `ticket_remote_spacetime_sidecar`; the public `ticket_remote` container must not receive it
- after login and a current membership check, the sidecar issues a five-minute member-proxy token using that key's real issuer and audience; the module separately pins its proxy role, `member:<email>` subject, verified email, and live membership, without granting service reducers
